# Account verification and restoration — 22 October 2026

Status: implemented and tested locally; not deployed. This supersedes the earlier source-level AUTH-03 gap. Production closure still requires migration, coordinated deployment and independent mailbox/device acceptance.

## Registration behavior

Platform `POST /app/v1/auth/register` never creates an account or returns a session. Public callers get HTTP 200 `{status: "ok", pending: true}` for valid signup data. Only the trusted Learner service can request a verification challenge; the same issuance path runs for new, existing and banned email addresses without an account-existence lookup. The trusted response's token is delivered by Learner and removed from the browser API response. The browser receives the same pending status/message. Delivery failure returns a service error; successful pending responses do not certify inbox receipt.

Challenges expire in one hour, store a SHA-256 token hash and salted PBKDF2 password hash, and are capped at five unexpired challenges per normalized address. Retries do not invalidate previously issued links. There is no automatic identity linking by matching contact email.

The bilingual mail links to `/verify-email#token=…`. The fragment keeps the token out of HTTP request URLs and access logs; the verification page uses `no-referrer`. Loading the link does not activate an account. The user submits the original signup password by POST. This prevents a signup initiated by another person from being activated merely by clicking their email link.

Verification atomically claims the unused token, creates the email account only if none exists, and invalidates other challenges for that address. Concurrent consumption has one winner; transaction failure rolls back consumption and creation. A successful new account records `email_verified_at` and schedules its welcome email. Verification never creates a login session; the user signs in separately. Existing accounts, passwords, bans and sessions are preserved, and existing-account completion uses the same response. Account deletion removes its outstanding challenges; the scheduled auth cleanup removes used/expired challenges.

Existing email accounts remain usable with `email_verified_at = NULL`; that is not a claim of historical mailbox ownership. Retrospective verification or enforcement for legacy accounts is a separate rollout decision.

## Cross-device restoration

Signed RSA fixture tests exercise native and approved web audiences for both Apple and Google. Two sessions with the same provider subject restore the same `path_u1` completion. Different subjects remain isolated even when contact emails match. Native token formats, progress payloads and provider-specific account keys are preserved.

These tests assume the identity provider returns the same grouped subject across the supported clients. They do not prove Apple dashboard grouping, user account selection, live provider exchanges or restoration on physical devices. No Apple/Google/email identity merge was added.
